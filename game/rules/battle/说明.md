# 战斗内核

战斗规则只负责一次自动战斗，不读数据库、不发消息，也不结算掉落、经验或灵石。

## 固定顺序

所有普通攻击、功法伤害、持续伤害、连击、反击和反伤都进入同一条流水线：

```text
原始伤害
-> 命中
-> 暴击与抗暴
-> 比例穿透、固定穿透与防御
-> 伤害加成与伤害减免
-> 格挡与破格
-> 最低伤害边界
-> 护盾
-> 血气
```

每段伤害分别记录判定值、中间数值、护盾伤害、血气伤害、过量伤害和结算前后资源。吸血只读取
血气伤害；反伤读取实际承受的直接伤害。多段功法按 `顺序执行` 拆成多次独立结算，前一段产生的
状态和触发会影响后一段。

## JSON 闭环

属性、资源、流程和原子能力保存在 `data/rules/战斗`；机制与词条保存在 `data/content/战斗机制`，
功法作为纳戒资产按类型保存在 `data/content/物品/功法`。功法在 `组成` 中组合固定属性、主动技能和被动技能。
`data/rules/战斗/战报.json` 保存战报协议、角色视觉、事件词典、格式字段和界面配置。启动加载时会同时校验：

- 每个原子能力绑定的执行器必须存在，能力类别必须与执行器职责一致。
- 功法、敌人、角色及机制内部的字段、嵌套、事件、属性、资源和机制引用必须符合能力 Schema。
- 未知字段、循环引用和当前执行器尚不接受的选项会直接阻止加载。

正式内容共有 264 个战斗方向。每个方向各有 9 门功法、9 本附魔技能书和 9 颗宝石，并用提供、需要、禁止
与互斥标签保证随机构筑可运转。方向不是“核心体系乘精通后缀”的换名产物：审查器会剔除名称、状态名和
机制计量名，再比较完整能力树；264 个方向必须得到 264 个不同结果，否则测试直接失败。主动技能按全局唯一
`释放顺序` 选择，被动功法和附魔按全局唯一 `结算顺序` 触发；品级只缩放能力数值，不改变顺序、标签或循环结构。

正式规则与内容只保存在 `data`。当前运行层已落实数值计算、随机选择、资源
恢复/消耗/设置/转移、状态层数与持续时间、净化免疫、行动进度、冷却和复生等单体战斗语义；机制按
持续伤害、护盾、储能、印记、资源、控制等类别拆入正式目录。把母本中的一项能力正式搬入 `data` 时，必须先
判断能否由现有原子能力组合；能组合就只写 JSON。只有出现全新底层语义时才增加执行器，再在
`原子能力.json` 声明字段规则并补回归测试。

左右阵营已经支持多名参战者，共用统一速度队列并从存活敌方中选择目标。机制计量支持增减、设置、清空、
上下限和不足失败；技能蓄势可跨连续遭遇继承；追击和反击使用受硬上限约束的真实追加行动；分摊与转移在
原目标受伤前进入统一伤害预结算，并限制为同阵关系、防止递归承伤。召唤单位、场域阵法和站位距离仍未定义，
继续只保留在设计母本，不得以空执行器或无效字段冒充已经支持。

## 行动与连续遭遇

开场双方各行动一次；之后速度按递减收益公式积累行动进度，速度再高也不会无限连动。多本已装配
功法的可用主动招式按轮转顺序选择，后装配功法不会被前面的短冷却招式长期挤掉。

战斗入口接收左右两组 `CombatantSnapshot`，并保留后端提供的类别和等级。所有参战者都由相同流程装配
属性、主动技能、被动技能、冷却、状态、丹药和招式游标；本命武器与功法由修士资源负责提供，灵兽可只用
自身属性和基础攻击。核心没有玩家专用、道侣专用或敌方专用结算分支。战报按阵营判胜，同时为每名参战者
保留独立编号、颜色、资源和事件归属。

探险在同一组六轮预计算中继承血气、精神、体力、护盾、临时状态、技能冷却、主动招式轮转位置和
丹药余量。每个敌人实例使用独立稳定 ID；上一场留下的灼烧不会被错误记到下一名同名对手身上。

## 验证

```powershell
python -m unittest discover -s tests -v
python -X utf8 tools/audit_direction_mechanics.py
python -X utf8 tools/audit_battle_balance.py
```

测试只使用临时 SQLite 数据库，不读写 `data/game.db`。机制审查会忽略纯命名差异并拒绝重复能力树，报告
写入 `log/战斗机制审查.json`；平衡审查覆盖全部方向、三槽与六槽、全部品级以及真实战斗，报告写入
`log/战斗平衡审查.json`。
