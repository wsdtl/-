# 战斗内核

战斗规则只负责一次自动战斗，不读数据库、不发消息，也不结算掉落、经验或灵石。

## 固定顺序

所有普通攻击、功法伤害、持续伤害、连击、反击和反伤都进入同一条流水线：

```text
原始伤害
-> 命中
-> 暴击与抗暴
-> 比例穿透、固定穿透与防御
-> 伤害加成与伤害减免
-> 格挡与破格
-> 最低伤害边界
-> 护盾
-> 血气
```

每段伤害分别记录判定值、中间数值、护盾伤害、血气伤害、过量伤害和结算前后资源。吸血只读取
血气伤害；反伤读取实际承受的直接伤害。多段功法按 `顺序执行` 拆成多次独立结算，前一段产生的
状态和触发会影响后一段。

## JSON 闭环

属性、资源、流程和原子能力保存在 `data/rules/战斗`；机制与词条保存在 `data/content/战斗机制`，
功法按类型保存在 `data/content/功法`。功法在 `组成` 中组合固定属性、主动技能和被动技能。
`data/rules/战斗/战报.json` 保存战报协议、角色视觉、事件词典、格式字段和界面配置。启动加载时会同时校验：

- 每个原子能力绑定的执行器必须存在，能力类别必须与执行器职责一致。
- 功法、敌人、角色及机制内部的字段、嵌套、事件、属性、资源和机制引用必须符合能力 Schema。
- 未知字段、循环引用和当前执行器尚不接受的选项会直接阻止加载。

`基础数据/战斗` 是后续机制的设计母本，不进入运行链。把其中一项能力正式搬入 `data` 时，必须先
判断能否由现有原子能力组合；能组合就只写 JSON。只有出现全新底层语义时才增加执行器，再在
`原子能力.json` 声明字段规则并补回归测试。

## 行动与连续遭遇

开场双方各行动一次；之后速度按递减收益公式积累行动进度，速度再高也不会无限连动。多本已装配
功法的可用主动招式按轮转顺序选择，后装配功法不会被前面的短冷却招式长期挤掉。

战斗入口只接收左右两份 `CombatantSnapshot`，并保留后端提供的类别和等级。两方都由相同流程装配
属性、主动技能、被动技能、冷却、状态、丹药和招式游标；本命武器与功法由修士资源负责提供，灵兽可只用
自身属性和基础攻击。核心没有玩家专用或敌方专用结算分支。

探险在同一组六轮预计算中继承血气、精神、体力、护盾、临时状态、技能冷却、主动招式轮转位置和
丹药余量。每个敌人实例使用独立稳定 ID；上一场留下的灼烧不会被错误记到下一名同名对手身上。
