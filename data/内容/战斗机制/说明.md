# 战斗机制 JSON 关系说明

本目录保存可复用的战斗积木。机制位于原子能力和功法/附魔之间：它比原子能力具体，但不等于一门完整功法。

## 实体结构

每个文件是机制池数组，每个机制只有三个根字段：

```json
{
  "编号": "600001",
  "名称": "正锋",
  "节点": {
    "能力": "造成伤害"
  }
}
```

| 字段 | 作用 |
| --- | --- |
| `编号` | `60` 前缀稳定身份，供功法、附魔和规则引用 |
| `名称` | 战报和维护展示，不作为主键 |
| `节点` | 符合原子能力 Schema 的可执行能力树 |

当前共有 80 个文件、1600 个机制。文件名是机制池身份，编号是具体机制身份。

## 上游定义

机制节点只能使用：

- `定义/战斗/原子能力.json` 登记的能力名和字段；
- `定义/战斗/属性.json` 登记的属性名；
- `定义/战斗/资源.json` 登记的资源名；
- `定义/战斗/事件.json` 登记的事件名；
- 其他真实存在的机制编号。

机制可以通过 `引用战斗机制` 或 `引用被动机制` 嵌套复用，但必须受能力链深度和循环引用校验约束。

## 下游消费者

```text
功法.能力[].效果[].机制 ----------> 机制编号
附魔.能力[].效果[].机制 ----------> 机制编号
规则/构筑/相冲.json[].机制 ------> 机制编号
BattleEngine ----------------------> 展开节点并执行
战报 ------------------------------> 使用机制名称解释来源
```

功法通常组合多个主动和被动机制形成完整循环；每个附魔只监听一个被动机制；宝石不引用机制。

## 文件分类的意义

文件分类用于维护和以后配置候选池，不改变机制自身语义。同一个编号无论被哪个功法或附魔引用，节点都完全相同。不能复制一个机制只改名称后当作新机制。

## 修改检查

1. 新机制编号必须唯一且符合 `60` 前缀。
2. `节点` 必须通过原子能力递归 Schema 校验。
3. 引用其他机制时检查引用存在、没有环并且深度可控。
4. 修改已有节点会影响所有引用它的功法、附魔和构筑相冲关系。
5. 删除机制前必须全库搜索六位编号，而不是只搜索名称。
