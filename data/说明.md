# JSON 数据组合协议

本文档记录 `data` 目录当前数据如何被定位、引用、抽取、实例化、装配、结算和回写，供后续重构执行器使用。

JSON 是规则和内容的唯一事实源。本文档只解释 JSON 之间的组合关系，不得成为第二份配置；文档与 JSON 冲突时，以 JSON 为准并同步修正文档。游戏 Python 只负责读取和执行，不得另设固定数值、内容清单、专用组合表、评分或平衡规则；校核、评分和平衡由 `tools/` 中的游戏外脚本负责。

## 1. 数据边界

| 目录 | 职责 | 能否被运行期修改 |
| --- | --- | --- |
| `定义/` | 编号、品级、属性、资源、事件、原子能力词典 | 否 |
| `规则/` | 初始化、成长、修行、战斗和构筑规则 | 否 |
| `内容/` | 世界、敌人、道侣、物品、功法、附魔、宝石和战斗机制 | 否 |
| `展示/` | 战报标准化和界面词典 | 否 |
| `*.db` | 玩家资产、活动状态和运行日志 | 是 |

内容完整性与平衡审查属于开发辅助功能，其配置位于 `tools/战斗校验/`，不属于正式数据目录，也不进入运行期数据注册表。

开发发布顺序固定为：

```text
tools 读取全部正式 JSON
-> 内容完整性、引用、编号和能力树校核
-> 需要时执行评分与战斗平衡模拟
-> 校核通过后发布正式 data
-> game 读取已经发布的数据
-> 运行期按池抽取并生成实例
-> 战斗或玩法执行
-> 只回写运行期资产和结果
```

正式 JSON 必须先通过 `tools/` 的全部校核才能发布。游戏运行期不重复扫描全库、不计算评分、不判断方向是否平衡，也不得静默回退到代码默认内容；只在实际读取或执行所需数据失败时终止对应启动或玩法。

## 2. 文件加载与集合展开

### 2.1 文件身份

- 加载器递归读取 `data` 下全部 `.json`。
- 资源池引用使用文件名，不使用路径，也不逐个枚举文件内部对象。
- 引用值省略 `.json` 后缀。例如 `"功法-玄霜九转蚀骨"` 对应 `内容/物品/功法/功法-玄霜九转蚀骨.json`。
- `内容/` 中可被资源池按文件名引用的 JSON 必须全局唯一。`定义/`、`规则/` 和 `展示/` 按完整相对路径读取，不依赖文件名猜测职责。
- 同一文件内的对象按原始数组顺序或对象声明顺序稳定展开。
- 文件名和所在目录已经声明内容类别，JSON 根值不得再用同名类别键包装。编号集合直接使用数组，命名集合直接使用对象，单体文件直接使用该实体对象。
- `JsonDataReader.load_catalog()` 只注册 `定义/`、`规则/`、`内容/`、`展示/` 四类正式 JSON；`tools/` 中的辅助配置、数据库、备份和运行媒体均不进入正式数据注册表。
- JSON 使用严格解析，同一对象出现重复键时直接报错，不允许后值静默覆盖前值。
- 游戏加载器只完成四类目录注册、内容实体索引和玩法需要的引用展开。世界坐标、编号、跨池实体一致性和全库引用完整性由 `tools/` 在发布前审查。
- 游戏外审查器会一次汇总同类问题。相同编号若在不同文件中指向不同名称或实际能力定义，只按编号报告一项冲突，同时保留来源文件用于定位；仅说明、池内权重不同不构成编号冲突。

### 2.2 当前集合形态

| 内容 | 顶层形态 | 单项身份 |
| --- | --- | --- |
| 世界 | `{名称, 出生地, 坐标边界, ...}` | `地图规则.json` |
| 区域 | `{类别, 坐标范围, ...}` | 文件名 |
| 地点 | `{所属区域, 坐标, ...}` | 文件名 |
| 敌人 | `{名称: {...}}` | 对象键 |
| 道侣 | `[{...}]` | 六位编号 |
| 普通物品 | `[{...}]` | 六位编号 |
| 功法 | `[{...}]` | 六位编号 |
| 附魔 | `[{...}]` | 六位编号 |
| 宝石 | `[{...}]` | 六位编号 |
| 词条 | `{名称: {...}}` | 对象键 |
| 机制 | `{名称: 能力节点}` | 对象键 |
| 战斗方向 | `{方向名: {...}}` | 对象键 |

`定义/品级.json`同样直接使用品级数组，品级编号位数由`定义/编号.json -> 品级编号规则`统一登记。`定义/战斗/属性.json`直接使用属性名到属性定义的对象；`参战者必需属性`属于辅助完整性审查，保存在`tools/战斗校验/内容完整性.json`。

有编号的实体加载后以编号为主键，名称只用于展示和查找提示。没有编号的规则名、属性名、资源名、事件名、机制名、状态名和地点名仍以中文名称作为其所在注册表内的引用键。此规则适用于所有编号实体，不是宝石特例：同一编号无论出现在哪些方向和资源池，都表示同一个实体，其名称、属性、能力和其他实际定义必须一致。方向化说明和池内权重只属于池成员关系，不参与实体身份比较。

`评分`不属于实体定义。它只能由`tools/战斗校验/平衡.json`中的平衡工具根据实体实际定义计算，不得进入正式数据、内容实体、运行期实例、抽取权重、数据库外键、价格公式或玩家展示。

所有参战者最终都按属性注册表补齐缺省值；`参战者必需属性` 中的血气上限、精神上限、攻击、防御和速度必须能够在补齐后得到合法值。未登记属性不得静默进入面板。

## 3. 编号与引用

### 3.1 实体编号

实体编号由 `定义/编号.json` 统一解释：

```text
总长 6 位 = 2 位类别前缀 + 4 位稳定流水号
```

当前前缀：

| 前缀 | 实体 |
| --- | --- |
| `10` | 丹药 |
| `20` | 天材地宝 |
| `21` | 灵兽材料 |
| `30` | 修行器物 |
| `40` | 功法 |
| `41` | 附魔技能书 |
| `42` | 宝石 |
| `50` | 道侣 |

编号必须以字符串保存。编号创建后不可修改，不承载品级、地区、修行方向或强度。数据库和存档保存实体编号，不保存展示名称作为外键。

### 3.2 品级编号

品级是独立的两位编号：`01` 黄品、`02` 玄品、`03` 地品、`04` 天品、`05` 圣品。物品编号与品级编号必须分开保存：

```json
{
  "编号": "400001",
  "品级": "03"
}
```

不得把品级拼进六位实体编号。这样调整品级能力倍率时不需要迁移实体编号。

### 3.3 四类引用

| 引用对象 | 存储值 | 示例 |
| --- | --- | --- |
| 具体实体 | 实体编号 | `"100005"` |
| 品级 | 品级编号 | `"03"` |
| 资源池 | 文件名，不带后缀 | `"物品-天材地宝-沙地"` |
| 规则注册项 | 注册名 | `"攻击"`、`"造成伤害后"`、`"真火击"` |

资源池引用永远保持为池，不得在地点、道侣或敌人 JSON 中展开成固定实体编号列表。运行期可以展开池，但不得反写 JSON。

## 4. 权重、池与随机

### 4.1 统一权重

带 `权重` 的候选统一使用正整数逆权重：

```text
候选相对抽中率 = 1 / 权重
```

权重越高越稀有。权重只参与抽取，不参与属性、伤害、评分或价格计算。人物、敌人、普通物品、功法、附魔、宝石、品级和词条使用同一语义。

### 4.2 池展开

```text
读取池文件名数组
-> 按数组顺序找到文件
-> 展开各文件对应集合
-> 合并候选
-> 去重
-> 再执行一次对象级加权抽取
```

不得先抽文件再抽对象，否则拆分文件会形成隐含的第二层概率。编号实体按编号去重；无编号对象按所在集合的对象键去重。

### 4.3 放回规则

- 功法、附魔和宝石的当前标准构筑在一次生成中去重抽取，即同一构筑的同类槽位不重复。
- 功法词条按功法自己的 `随机词条` 池去重抽取，同一功法实例不能出现同名词条。
- 不同战斗、不同掉落或不同人物实例之间可以再次抽中相同实体。
- 能力节点 `随机执行` 是否放回由节点自己的 `是否放回` 决定，默认不放回。
- 当候选去重后少于所需数量时生成失败，不得自动降低槽位数。
- 加载器的池展开必须显式选择模式：`deduplicate=false` 保留各原池中的重复候选，`deduplicate=true` 按实体编号或对象键展开去重；调用方不得依靠隐含默认值猜测。

“保留池内重复”与“多个池展开后去重”的双模式目前还没有 JSON 字段表达，见第 18 节待补协议；执行器重构前不得自行增加隐式模式。

## 5. 品级与实例化

### 5.1 品级作用

品级定义提供五种规则：

| 字段 | 作用 |
| --- | --- |
| `阶序` | 比较“至少某品级”等范围 |
| `权重` | 随机品级的逆权重 |
| `能力倍率` | 放大线性能力数值 |
| `价格系数` | 放大普通物品参考价 |
| `词条数量` | 决定功法实例抽取多少条随机词条 |

### 5.2 普通物品实例

```text
基础物品
+ 品级
-> 使用效果中的恢复量乘能力倍率
-> 使用效果中的经验乘能力倍率并四舍五入为至少 1
-> 参考价乘价格系数并四舍五入
-> 形成可堆叠的品级物品实例
```

同一实体编号、不同品级必须分别堆叠。库存身份至少由 `(人物, 物品编号, 品级编号)` 组成。

### 5.3 功法实例

```text
按功法池抽取功法编号
-> 按品级池抽取品级编号
-> 读取该品级的词条数量 N
-> 从功法.随机词条中按逆权重无放回抽取 N 条
-> 每条词条在 [最小值, 最大值] 内独立取值
-> 保存功法编号、品级编号和已落定词条
```

词条取值边界为整数时取闭区间整数，否则取闭区间小数。词条数值落定后属于实例资产，不能因重新加载 JSON 再次随机。

功法实例不保存评分。平衡工具需要评估某个实例时，临时读取功法、品级和已经落定的词条计算参考结果；计算结果不反向改变实例，也不成为加载或抽取条件。品级能力倍率不再乘已经落定的词条数值。

### 5.4 附魔和宝石实例

```text
按池抽取实体编号
-> 独立抽取品级编号
-> 保存实体编号和品级编号
-> 战斗展开时读取实体.组成
```

附魔和宝石 JSON 同时承担物品底座和战斗能力定义，不再生成第二份重复内容 JSON。

### 5.5 能力倍率边界

`tools/战斗校验/平衡.json` 当前规定：

- 线性数值乘 `能力倍率`。
- 概率放大后不得超过对应原子能力字段上限。
- 持续时间、释放顺序、结算顺序和兼容标签不随品级改变。
- 固定属性、伤害、恢复、护盾、资源变化和状态内线性数值都属于能力树的一部分。

具体哪些嵌套数字属于“线性数值”尚未在 JSON 中给出机器可读路径，重构时必须先补齐，不能用“遍历所有数字并相乘”的方式实现。

## 6. 世界、地点与遭遇池

### 6.1 世界层级

```text
地图规则.世界
-> 区域文件.区域
-> 地点文件.地点
-> 地点引用的道侣池、敌人池、天材地宝池
```

- 世界使用 `(x, y, z)` 三轴坐标并提供出生地和三轴边界。`x`、`y` 描述当前位面的平面位置，`z` 保留给位面层级。
- 当前世界和全部区域的 `z轴` 边界固定为 `[0, 0]`，所有地点坐标第三位必须为 `0`；高位次元内容及跨层通行规则暂不定义。
- 区域提供自己的三轴坐标范围。
- 地点坐标必须使用 `[x, y, z]`，位于世界边界和所属区域范围内；三轴坐标组合必须全局唯一。
- 地点只通过 `可用功能` 开放玩法，不另设安全/危险字段。
- 启用 `修士` 必须有道侣池；启用 `探险` 必须有敌人池。
- 未启用相应功能的地点不得暗藏对应资源池。

### 6.2 道侣池

地点 `道侣池` 引用同地点的道侣文件。道侣不是独立角色类型，而是与玩家建立关系的修士。每名道侣显式声明：

```text
角色类型 = 修士
+ 成长规则 = 修士
+ 修行方向
+ 资质范围
+ 属性覆盖与实力波动
+ 功法池
+ 附魔池
+ 宝石池
```

首次入队生成顺序：

```text
读取 修士成长规则.属性基准
-> 取得 37 项属性定义默认值
-> 应用道侣.属性覆盖
-> 对实力波动字段分别抽取倍率
-> 在资质范围内抽取资质
-> 按道侣规则生成 3/3/3 同行构筑
-> 保存已经落定的属性、资质和构筑实例
```

离队只改变关系，不重随机道侣属性和构筑。好感上限、同行槽位和资质成长修正统一来自 `规则/道侣.json`。

资质只修正道侣以后获得的修士每级属性成长，不修改一级属性：

```text
位置 = (资质 - 资质范围最低值) / (资质范围最高值 - 资质范围最低值)
成长倍率 = 最低倍率 + 位置 × (最高倍率 - 最低倍率)
```

当前位置固定在 `[0, 1]`；当前倍率范围为 `[0.75, 1.25]`。资质范围两端相同时使用 `范围同值倍率=1`。

### 6.3 敌人池

地点 `敌人池` 引用同地点敌人文件。一次遭遇生成顺序：

```text
按敌人权重抽取敌人
-> 在等级闭区间抽等级
-> 取得 37 项属性定义默认值
-> 应用敌人.属性覆盖
-> 修士引用 成长/修士，灵兽读取自身每级成长
-> 基础属性 + (等级 - 1) × 对应每级成长
-> 对实力波动列出的属性分别抽倍率并相乘
-> 生成本次遭遇快照
-> 战斗胜利后独立结算灵石、物品和本命武器经验
```

所有敌人使用 `角色类型` 区分修士与灵兽。敌方修士显式声明 `成长规则=修士`，与玩家、道侣共用等级成长；灵兽保留自身 `每级成长`。实力波动只作用于 `实力波动.属性` 列出的字段，每个字段独立抽取 `[最低倍率, 最高倍率]` 内的整数百分比。

敌人掉落的 `物品池` 仍引用文件。池非空时，每次胜利从展开后的对象池抽取一个物品，再独立抽品级；引用处不重复填写概率。空池表示没有物品掉落，不影响灵石和本命武器经验。

## 7. 构筑组合

### 7.1 方向池

一个正式战斗方向由同名的三类文件共同组成：

```text
功法-<方向>.json
物品-附魔-<方向>.json
物品-宝石-<方向>.json
```

三类池文件只保存各自的候选数组。方向说明集中保存在`内容/战斗方向.json`，不混入任何功法池。当前完整性目标为 264 个方向，每个方向的功法、附魔和宝石候选各不少于 9 项。

### 7.2 槽位职责

`规则/战斗/构筑.json` 当前规定：

| 功法槽位 | 主动功法最少 | 被动功法最少 |
| --- | --- | --- |
| 3 | 1 | 1 |
| 6 | 3 | 3 |

最低数量不是精确配比。只要同时满足最低值，剩余槽位可以是主动或被动。

### 7.3 标签兼容

功法、附魔和宝石共用四个兼容字段：

- `提供标签`：该项向整个构筑提供的能力标签。
- `需要标签`：必须由其他已选项提供；自身提供不能满足自身需要。
- `禁止标签`：其他已选项提供任一禁止标签即冲突。
- `互斥组`：同一互斥组最多出现一项。

一套构筑合法，当且仅当：

```text
所有需要标签均由其他项提供
且所有禁止标签均未由其他项提供
且每个互斥组最多一项
且主动/被动职责满足对应槽位规则
```

生成器最多尝试 200 套候选。达到上限仍无合法解时必须报错，不得忽略标签或职责继续生成。

### 7.4 普通敌方修士与首领

| 类型 | 候选范围 | 功法/附魔/宝石槽位 |
| --- | --- | --- |
| 普通 | 先随机一个方向，再使用该方向三池 | 6/6/6 |
| 首领 | 从全池筛选最多 3 个兼容战术 | 6/6/6 |

全池首领先从功法 `提供标签` 中提取 `战术:` 标签，筛除互相禁止的战术，再用选中战术过滤三类候选，最后执行普通兼容校验。

## 8. 能力树组合语法

### 8.1 三层结构

```text
内容实体.组成
-> 装配节点
-> 主动/被动节点中的效果树
-> 可选引用机制库中的具名节点
-> 最终落到原子执行器
```

`定义/战斗/原子能力.json` 是能力语法和字段 Schema。能力节点必须有 `能力` 字段，执行器只按该能力定义中的 `执行器` 路由，不能按功法名、机制名或状态名写分支。

### 8.2 装配节点

`组成` 当前允许三类根节点：

| 能力 | 组合结果 |
| --- | --- |
| `固定属性加成` | 把属性表加入人物面板 |
| `主动技能` | 生成按释放顺序轮转的主动技能 |
| `被动技能` | 生成按结算顺序监听事件的被动技能 |

主动技能效果只允许组合、效果或引用类别。被动技能效果只允许 `监听事件` 或 `引用被动机制`。

### 8.3 机制引用

- `引用战斗机制` 只能引用组合或效果节点。
- `引用被动机制` 只能引用触发节点。
- 引用在执行前解析为机制注册表中的节点，但保留来源实例，便于倍率、状态来源、触发上限和战报追踪。
- 机制引用不得形成循环；当前 JSON 尚未单独声明最大引用深度，校验器必须至少执行循环检测。

### 8.4 原子能力类别

| 类别 | 当前能力 |
| --- | --- |
| 装配 | 固定属性加成、主动技能、被动技能 |
| 引用 | 引用战斗机制、引用被动机制 |
| 组合 | 顺序执行、条件执行、随机执行 |
| 触发 | 监听事件、状态周期触发 |
| 数值 | 读取数值、计算数值、随机数值 |
| 目标 | 选择目标、选择自身、选择技能 |
| 条件 | 概率条件、数值条件、状态条件、类型条件、组合条件、标签条件 |
| 效果 | 造成伤害、恢复资源、消耗资源、设置资源、转移资源、添加状态、移除状态、增加状态层数、消耗状态层数、延长状态、缩短状态、复制状态、转移状态、修改行动条、修改技能冷却、修改机制计量、追加攻击、分摊伤害、转移伤害、抵挡致命伤害、复活 |

所有字段类型、默认值、枚举、最小值、最大值和嵌套类别继续直接读取 `定义/战斗/原子能力.json`，不得在代码中复制第二套 Schema。

### 8.5 数值树

`读取数值` 可以从固定值、人物属性、当前资源、本次事件、状态层数和机制计量读取。读取结果按以下顺序处理：

```text
读取来源原值
-> 乘百分比 / 100
-> 应用节点最低值和最高值
-> 返回数值
```

`读取时机=执行时` 每次执行重新读取；`施加时快照` 在状态施加时固定来源值，后续周期触发不得重新读取来源当前面板。

`计算数值` 支持相加、相减、相乘、相除、最小、最大和平均，可以递归组合数值节点。`随机数值` 在动态上下界之间抽取，是否取整由节点决定。

## 9. 角色数据、属性和资源

### 9.1 三种对象

| 对象 | 示例 | 是否持久化 |
| --- | --- | --- |
| 角色事实 | 角色类型、成长规则、等级、经验、装备编号和所属关系 | 是 |
| 常驻属性面板 | 血气上限、攻击、速度、暴击率等 37 项 | 应由事实和 JSON 派生 |
| 战斗快照 | 常驻面板副本、当前资源、状态、冷却、计量 | 只在本场战斗存在 |

不进入战斗时角色仍然有可计算的常驻属性，只是不创建战斗快照。数据库应优先保存生成事实和实例结果，不重复保存能够从 JSON 重新计算的整张面板。

玩家、道侣和敌方修士不是三套角色：

```text
修士
├─ 玩家：使用 初始/人物.json 增加出生资产
├─ 道侣：增加身份、结交、资质和同行关系
└─ 敌方修士：增加战斗策略、掉落和交锋所得
```

三者均声明 `角色类型=修士`、`成长规则=修士`，共同引用 `规则/成长/修士.json`。道侣身份和敌对身份不能产生第二套属性或成长公式。

### 9.2 出生属性

玩家创建顺序：

```text
读取 规则/初始/人物.json 的 成长规则
-> 读取 规则/成长/修士.json 的 属性基准
-> 取得全部属性定义默认值
-> 使用 初始人物.属性覆盖 替换同名默认值
-> 初始化等级、经验、灵石、状态、自动用药和物品
-> 当前血气/精神取对应上限，当前护盾取 0
```

当前一级核心属性：

```text
血气上限 100
精神上限 100
攻击 5
防御 0
速度 100
```

未覆盖的其余属性继续使用 `定义/战斗/属性.json` 默认值。

### 9.3 等级成长

修士属性从 2 级开始成长。等级 `L` 的成长次数为 `max(0, L - 1)`：

```text
等级属性 = 出生属性 + (L - 1) × 每级成长
```

当前修士成长：血气上限每级 12、精神上限每级 6、攻击每级 0.5、防御每级 1。速度及其他属性没有修士等级成长时保持原值，由装备、功法或状态改变。玩家和敌方修士使用 1 倍成长；道侣再乘已经落定的资质成长倍率。

修士和本命武器当前升级所需经验均使用各自 JSON 中的：

```text
当前等级所需经验 = 基础 + 等级平方系数 × 当前等级²
```

达到等级上限后不再升级。

### 9.4 本命武器

本命武器等级 `W` 的攻击：

```text
武器攻击 = 基础攻击 + (W - 1) × 每级攻击
```

当前一级本命武器攻击为 10，每级增加 1，最高 100 级，并提供 6 个附魔位和 6 个宝石位。

### 9.5 常驻属性面板

完整组合顺序：

```text
属性默认值
-> 出生覆盖
-> 修士等级成长
-> 其他永久成长
-> 本命武器攻击加入攻击
-> 已装备功法实例词条
-> 功法固定属性 × 功法品级能力倍率
-> 附魔固定属性 × 附魔品级能力倍率
-> 宝石固定属性 × 宝石品级能力倍率
-> 按属性定义的最低值和最高值裁切
-> 角色常驻属性面板
```

`属性覆盖` 在角色实例生成时替换属性基准中的同名值；未覆盖字段继续使用属性默认值。同名固定属性加成一律相加，不能与覆盖语义混用。

`最小单位` 已经在属性定义中登记，但当前没有声明采用四舍五入、向下取整还是保留计算精度，因此不能由执行器自行选择，见第 18 节。

### 9.6 资源

资源与上限属性的关系由 `定义/战斗/资源.json` 注册：

```text
血气 ∈ [0, 血气上限]
精神 ∈ [0, 精神上限]
护盾 ∈ [0, 护盾上限]
```

上限是属性，当前值是资源。任何恢复、消耗、设置、转移、出生、开战或战后回写都必须经过资源边界裁定。

## 10. 战斗快照与开战组合

开战时按参战者逐人生成快照：

```text
读取人物常驻面板
-> 复制为本场基础面板
-> 读取当前血气、精神、护盾并裁定到本场上限
-> 展开已装备功法、附魔、宝石能力树
-> 装配主动技能并按释放顺序排序
-> 装配被动技能并按结算顺序排序
-> 恢复需要跨连续遭遇保留的状态、冷却和轮转游标
-> 初始化本场机制计量和行动条
-> 触发战斗开始
```

临时状态属性只加入本场有效面板，不得写回常驻面板。状态移除或战斗结束后应自然消失；只有玩法规则明确要求跨连续遭遇保留的状态，才回写活动会话。

## 11. 时间条、行动与冷却

### 11.1 行动效率

`规则/战斗/行动.json` 声明标准速度 100、最低有效速度 25、最高行动效率 2 以及全部链深度、追加攻击、
召唤物和构造物上限。执行器按以下连续公式推进：

```text
有效速度 = max(速度, 最低有效速度)
行动效率 = 最高行动效率 × 有效速度
          / (有效速度 + (最高行动效率 - 1) × 标准速度)
```

每个时间窗把行动效率加入行动条；行动条每满 1 产生一次主行动，余数保留。公式是行动条执行器的固定语义，
参数和边界只从 JSON 读取；不存在蓄势、读条或第三套时间系统。

### 11.2 行动开始

自身行动开始时：

```text
触发行动开始事件
-> 恢复 血气恢复 点血气
-> 恢复 精神恢复 点精神
-> 推进技能剩余冷却
-> 选择可执行技能或普通攻击
```

冷却单位是“自身行动”，推进时点是行动开始、技能选择前，每次推进 1。

### 11.3 技能冷却与消耗

```text
实际冷却行动 = ceil(基础冷却行动 × (1 - 冷却缩减 / 100))
实际精神消耗 = 基础精神消耗 × max(0, 1 - 精神消耗修正 / 100)
```

实际冷却还必须受属性定义中的冷却缩减上下限约束。核心从可用技能中选取技能；技能在施放前被取消或事务代价
失败时，本次主行动改为普通攻击。

### 11.4 追加攻击

追加攻击属于当前主行动，不是新的时间条行动：

- 不再次推进冷却。
- 不再次扣减状态持续时间。
- 不触发新的行动开始和行动结束。
- 每次主行动最多追加 3 次，能力节点可以设置更低上限，取更严格者。

## 12. 事件与被动触发

事件名称只能引用 `定义/战斗/事件.json`。主干顺序为：

```text
战斗开始
-> 行动开始
-> 普通攻击后 / 追加攻击后 / 技能施放后
-> 命中、暴击、格挡、伤害、恢复、护盾和资源派生事件
-> 致命、死亡与击杀事件
-> 行动结束
-> 战斗结束
```

同一事件内的被动默认按所属被动技能的 `结算顺序` 排序；监听节点显式填写 `优先级` 时使用该值。监听器还受
事件关系、条件、递归栈、每次行动和每场战斗触发上限约束。

`受到致命伤害` 的监听效果必须且只能包含一个 `抵挡致命伤害` 执行器，避免同一监听器内出现多个互相覆盖的保命裁定。

## 13. 状态组合

状态由 `添加状态` 节点即时生成，身份至少由状态名和叠加范围共同决定：

- `同名共享`：不同来源的同名状态进入同一组。
- `按效果来源分组`：不同来源分别保有同名状态。

重复应用按 `重复方式` 处理：不叠加、刷新持续、延长持续、增加层数、增加层数并刷新或高值覆盖。层数不能超过 `层数上限`。

状态属性加入承受者本场有效面板；状态层数随状态组保存，但属性是否逐层线性叠加尚未由 JSON 声明。控制状态可进行控制判定：

```text
控制成功率 = 基础控制命中率
             + 来源控制命中率
             - 目标控制抵抗率
```

若受韧性影响：

```text
实际持续行动 = ceil(基础持续行动 × (1 - 韧性 / 100))
```

持续单位为 `状态承受者行动` 时，在对应事件结束后扣除；`整场战斗` 不按行动扣除。状态的行动限制和效果免疫在相应执行器执行前检查。

控制成功率最终裁定在 0 至 100%；状态属性按有效层数线性叠加。

## 14. 伤害组合

当前战报要求的伤害步骤为：

```text
原始伤害
-> 命中判定
-> 暴击
-> 穿透与防御
-> 伤害加成与伤害减免
-> 格挡
-> 最低伤害
-> 护盾吸收
-> 血气扣除
```

进入流水线前先形成原始伤害：

```text
普通攻击原始伤害 = 攻击 × max(0, 1 + 普通攻击威力 / 100)
技能原始伤害 = 能力数值 × 品级能力倍率 × max(0, 1 + 技能威力 / 100)
追加攻击原始伤害 = 攻击 × 追加攻击.威力倍率 / 100 × 品级能力倍率
```

`规则/战斗/伤害.json` 保存基础命中率、命中上下限、暴击倍率上限、格挡率上限、伤害倍率上限、防御常数和
最低伤害。伤害执行器使用下列固定流水线语义，所有参数只从该 JSON 读取：

```text
命中率 = clamp(攻击方命中率 - 目标闪避率, 最低命中率, 最高命中率)
暴击率 = clamp(攻击方暴击率 - 目标抗暴率, 0, 100%)
暴击倍率 = clamp(攻击方暴击伤害 - 目标暴击伤害减免, 100%, 最高暴击倍率)

有效防御 = 目标防御 × (1 - 比例穿透) - 固定穿透
有效防御 >= 0 时：防御倍率 = 防御常数 / (防御常数 + 有效防御)
有效防御 < 0 时： 防御倍率 = 2 - 防御常数 / (防御常数 - 有效防御)

伤害倍率 = clamp(1 + 伤害加成 - 伤害减免, 0, 最高伤害倍率)
格挡率 = clamp(目标格挡率 - 攻击方破格率, 0, 最高格挡率)
格挡后伤害 = 格挡前伤害 × (1 - 格挡减伤)
```

`无视防御` 跳过防御层但仍结算增减伤和格挡；`真实` 跳过防御、增减伤和格挡。最终正伤害不低于 `最低伤害`，先扣护盾再扣血气。

直接伤害、持续伤害、反伤、分摊和转移都必须走统一伤害流水线，并依据能力节点决定能否暴击、格挡和吸血。吸血按实际造成的血气伤害计算，不包含护盾吸收；反伤按实际承受的直接伤害计算，包含护盾吸收。

伤害后的派生反应：

```text
吸血恢复 = 实际血气伤害 × 吸血率 / 100
连击触发率 = 连击率
连击原始伤害 = 本次攻击原始伤害 × 连击伤害 / 100
反伤原始伤害 = 实际承受的直接伤害 × 反伤率 / 100
反击触发率 = 反击率
反击原始伤害 = 反击者攻击
```

连击、反伤和反击都是派生伤害，不能再次引发连击、反伤或反击链。反伤使用真实伤害，不能暴击和格挡；反击走普通直接伤害流水线。

### 14.1 恢复与护盾

`恢复资源` 先计算能力数值并乘品级能力倍率，再按资源类型修正：

```text
血气恢复 = 基础恢复 × max(0, 1 + 治疗加成 / 100 + 受疗加成 / 100)
护盾获得 = 基础护盾 × max(0, 1 + 护盾加成 / 100 + 受盾加成 / 100)
精神恢复 = 基础恢复
```

实际获得量还要受对应资源上限限制。事件中的 `本次恢复` 和 `本次护盾` 读取实际获得量，不读取溢出前数值。

## 15. 修行玩法组合

### 15.1 闭关

```text
持续上限 3600 秒
每 600 秒形成一轮
每轮获得 15 经验
感悟功法概率 0.35
圆满时清除临时状态
```

最多形成 6 个完整轮次。未满一轮不产生该轮收益。`感悟功法概率` 是每轮判定还是整次闭关判定，当前 JSON 未明确，执行器重构前必须补字段。

### 15.2 探险

```text
持续上限 3600 秒
每 600 秒一轮
最多 6 轮
每场战斗最多 80 个行动
自动用药阈值为血气上限的 30%
```

探险不再消耗体力。每轮使用上一轮战后资源、允许保留的临时状态、冷却和轮转游标进入下一场；只结算玩家已经完成并领取的轮次。

## 16. 战后回写

战斗结果分为三类：

| 数据 | 战后处理 |
| --- | --- |
| 永久事实 | 等级、经验、物品、装备实例继续保留 |
| 当前资源 | 按玩法规则保存战后血气、精神、护盾 |
| 临时战斗数据 | 状态、冷却、计量、行动条默认销毁；连续遭遇明确要求时写入活动会话 |

战斗临时属性绝不能写回人物基础属性。奖励在战斗核心之外结算；战斗核心只返回胜负、逐人资源、状态、冷却和物品消耗事实。

## 17. 游戏外校核与平衡审查

正式数据发布前，`tools/` 至少完成：

1. 全部 JSON 可解析且无重复键。
2. 可按文件名引用的内容文件全局唯一；每个六位实体编号只能对应一份实际定义，但允许同一实体作为成员出现在多个池中。
3. 编号前缀与所在实体类别一致。
4. 属性、资源、事件、能力、机制、具体实体和池引用全部存在。
5. 资源池非空，方向三池各不少于 9 项。
6. 3 槽和 6 槽都至少存在一套满足标签、互斥组和职责规则的构筑。
7. 主动释放顺序和被动结算顺序全局唯一。
8. 能力树符合原子能力字段 Schema，不存在引用循环。
9. 264 个方向剔除名称、状态名和机制计量名后仍保持 264 棵不同能力树。

平衡审查与内容完整性校核分开执行。`tools/战斗校验/内容完整性.json` 和 `tools/战斗校验/平衡.json` 只由辅助脚本按需读取，游戏启动不会加载。平衡审查覆盖 3/6 槽及全部 5 个品级，评分维度权重合计为 100；方向差距目标为 30%，达到 50% 时标记严重偏差。每方向抽 12 套构筑、每组对战使用 3 个种子、单场上限 120 行动。审查结果只服务于开发维护，不参与实体身份、内容加载、随机抽取、实例生成、价格、战斗、存档或玩家展示。

## 18. 当前待补协议

以下是基石之外仍需随人物成长、二次战斗对象和玩法结算继续明确的协议，不构成旧战斗内容兼容要求：

| 缺口 | 当前情况 | 重构前处理 |
| --- | --- | --- |
| 属性合成规则文件 | 顺序只散落在实现和本文 | 新增机器可读的属性来源、相加/覆盖、归一化时点 |
| 属性最小单位 | 有最小单位，无取整方式 | 为数值属性和百分比属性声明统一精度规则 |
| 品级倍率路径 | 只写“线性数值” | 明确各原子能力哪些字段随品级缩放 |
| 池去重模式 | 没有模式字段 | 对所有实体明确按原池抽取或展开去重抽取，以及单次构筑是否允许重复 |
| 初始物品品级 | 初始人物只写物品编号和数量 | 补品级编号或明确统一初始品级 |
| 闭关感悟次数 | 只有一个概率 | 明确按轮还是按整次判定 |
| 战斗资源回写 | 不同玩法可能不同 | 分玩法声明血气、精神、护盾和临时状态回写策略 |
| 名称引用遗留 | 个别内容仍用物品名或品级名 | 迁移为实体编号和品级编号 |
| 跨池实体一致性 | 同一编号允许出现在多个池 | 展开时按编号去重；加载时校验所有实际定义一致，池内说明和权重留在池关系中 |

这些协议补齐前，各玩法不得自行猜测或复制战斗规则；属于战斗基石的行为继续统一由原子执行器承担。

## 19. 执行器重构入口

新执行器建议只保留以下阶段接口：

```text
load_definitions()
load_rules()
load_content()
resolve_references()

expand_pool(file_ids)
roll_entity(pool, rng)
roll_grade(rng)
roll_loadout(direction_or_global_pool, slots, rng)

build_character_facts(save_data)
derive_persistent_attributes(character_facts)
build_combat_snapshot(character_facts, activity_state)

assemble_ability_tree(snapshot)
run_battle(snapshot_groups, rng)
settle_activity(battle_result, activity_rules)
```

`validate_all()` 不属于游戏执行器，它只能存在于 `tools/`。上述游戏接口只接受结构化数据和随机种子；代码不认识具体功法、宝石、附魔、敌人或道侣名称；新增内容只改 JSON，只有新增 `定义/战斗/原子能力.json` 尚未登记的底层语义时才增加一个最小执行器。
