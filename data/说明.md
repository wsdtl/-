# data 数据关系总览

`data` 是游戏定义、规则、内容和展示契约的唯一正式来源。Python 只读取、索引和执行这些 JSON；校核、评分、平衡和生成脚本属于 `tools`，不得成为运行时规则来源。

## 目录职责

| 部分 | 回答的问题 | 详细说明 |
| --- | --- | --- |
| `定义` | 有哪些编号、品级、属性、资源、事件、行程指标和原子能力 | [定义/说明.md](定义/说明.md) |
| `规则` | 初始化、成长、修行、行程和战斗怎样计算 | [规则/说明.md](规则/说明.md) |
| `内容` | 世界中实际有哪些地点、道路、角色、物品和机制 | [内容/说明.md](内容/说明.md) |
| `展示` | 游戏事实怎样转成战报、行程文字和界面数据 | [展示/说明.md](展示/说明.md) |

`.runtime/game.db`、`.runtime/runtime_log.db`、`.runtime/backups` 和 `.runtime/runtime_log_media` 是运行期数据，不属于 `data`。`data` 根目录只保留正式 JSON 及其说明文档。运行期数据库只能保存实体编号、实例状态和必要结果，不能复制 JSON 规则正文。

## 总关系

```text
定义/编号.json ───────────────> 内容中的六位实体编号
定义/品级.json ───────────────> 物品、功法、附魔、宝石实例的品级

定义/战斗/{属性,资源,事件,原子能力}.json
            │
            ├──> 规则/战斗/*.json
            ├──> 内容/战斗机制/*.json
            └──> 内容/物品/{功法,附魔技能书,宝石}/*.json

定义/行路/行程指标.json
+ 内容/世界/{地图规则,地势,道路/*.json}
            └──> 规则/行路/行程.json
                        └──> 展示/行程.json

规则/角色/*.json 与 规则/玩法/*.json
            └──> 未来人物、道侣、闭关和探险业务

规则/构筑/{生成,相冲}.json
            └──> 功法、附魔和宝石的合法组合生成

内容/世界/*.json
            ├──> 内容/世界/**/地点.json
            ├──> 内容/世界/**/道侣.json
            ├──> 内容/世界/**/敌人.json
            ├──> 内容/物品/灵材/*.json
            └──> 内容/物品/兽宝/*.json

战斗执行结果 ────────────────> 展示/战报.json ──> 结构化战报和静态战报页
```

## 四种引用

| 引用目标 | JSON 中保存什么 | 示例 |
| --- | --- | --- |
| 具体编号实体 | 六位编号字符串 | `"400001"`、`"600001"` |
| 品级 | 两位品级编号 | `"01"` |
| 资源池 | 内容文件名，不带 `.json` | `"物品-灵材-溪谷"` |
| 定义或规则注册项 | 注册名 | `"攻击"`、`"血气"`、`"造成伤害后"` |

资源池引用不能改成路径，也不能在引用处复制完整实体。只保存引用的池直接使用字符串列表：具体实体写六位编号，源池写不带 `.json` 的文件名。`内容` 下所有 JSON 文件名必须全局唯一，因为加载器会抹平目录层级并按文件名寻找资源池。

## 加载与执行顺序

```text
JsonDataReader 固定读取 定义/数据读取规则.json
-> 按规则扫描四个作用域，每份 JSON 必须唯一匹配一个数据集和文档形态
-> GameDataLoader 根据规则建立 文件名到池、身份到实体 的只读索引
-> 递归展开资源池
-> 校验编号前缀、池引用和循环引用
-> 各业务服务按数据集取得文件并校验自身业务约束
-> BattleEngine 执行战斗基石和二次对象
-> BattleReportCatalog 按展示 JSON 生成战报

未来移动执行器读取地图、地势、道路和行程规则
-> 生成结构化行程事实
-> 按展示/行程.json 生成玩家行程文字
```

`JsonDataReader` 会拒绝重复 JSON 键、重复内容文件名、未匹配规则和同时匹配多条规则的正式文件。`文档形态` 只描述对象、字典列表、编号实体列表、命名实体字典、命名实体或引用池等通用结构；功法、世界、角色等含义由取得相应数据集的服务解释。文件名已经表达的类别不能再在根节点外包一层同名键。

## 修改检查顺序

1. 先判断改动属于定义、规则、内容还是展示。
2. 新增、移动或改名文件时先检查 `定义/数据读取规则.json`，保证只命中一个数据集。
3. 修改定义时检查所有按名称引用它的规则、机制和内容。
4. 修改编号实体时保持编号不变；改名只影响展示，不得修改引用主键。
5. 修改池文件名时全库更新池引用，并保证新文件名仍全局唯一。
6. 修改战斗原子能力时同步检查机制、功法、附魔、战斗规则和战报表达。
7. 修改 JSON 后运行完整测试；平衡审查只在 `tools` 中运行。
